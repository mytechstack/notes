Context engineering for the SDLC

A shared memory system so every AI coding agent — in your IDE, in CI, running on its own — starts from the same grounded picture of your code, instead of starting from zero.

01 — Problem

What we're actually solving

AI coding agents are good at writing code. They're bad at knowing your code — what already exists, what conventions your team follows, what's actually broken in production right now, and who owns what.

Today, every agent session starts from zero. A developer pastes in a doc, re-explains a convention for the tenth time, or the agent just guesses and gets it plausibly wrong. None of that is a model problem — it's a memory problem.

Context engineering is building that memory once, as a shared platform capability, so every developer's agent starts from the same grounded picture — not whatever they happened to paste in that day. That's what makes a team agent-ready, not just a few developers who've each figured out their own tricks.

What it costs if we don't

  • Adoption stalls. Wrong-often-enough output means developers stop trusting agents and quietly go back to doing it by hand.
  • Trust stays uneven. One developer's agent is well-grounded because they pasted in the right docs; another's isn't. The team never becomes reliably agent-ready — it's a handful of people who've figured out their own workarounds.
  • Every team reinvents it. Without a shared setup, each team hand-rolls its own context-stuffing, badly and inconsistently.

Why five sources, not three

Local, platform, and external context describe what's supposed to be true — the design, the standard, the contract. Two more sources describe what's actually true right now: process context (is this ticket done, did CI pass, is this PR blocked) and runtime context (is this actually broken in production, what do the real logs say). An agent without the second kind is reasoning from the manual, not the machine. Note the two aren't equal effort — process context is usually just wiring, since GitHub, Jira, Linear, and CI providers already ship their own MCP servers; runtime context is the one you'll actually have to build.

Why a gateway, not five separate connections

Without one, every agent — your IDE assistant, your CI bot, your background migration agent — ends up with its own copy of the retrieval logic, and its own bugs. Build "how to search the platform catalog" once, in the gateway, and every agent gets it for free — including the next one you add.

Why trust & memory

Two problems only show up once agents are trusted with real work: context goes stale (a design doc from last year is confidently wrong), and some context shouldn't reach every agent (a security doc, a credential path). This layer timestamps and scopes every answer, and keeps a record of what agents got corrected on — so the correction sticks instead of being relearned every session.

What the gateway actually does

Concretely, it's an MCP server — or a router sitting in front of several MCP servers — that every agent connects to instead of connecting to each source on its own.

One call in, several sources out

"what does payments-svc do, and is it having issues right now?" → gateway → fans out to platform catalog + runtime → one merged answer

  • One place to change, not five. Swap the wiki tool or add a new source and you update the gateway once — every agent picks it up automatically.
  • One place for access rules. Who's allowed to see what is enforced once, not reimplemented per agent — which is where the holes usually creep in.
  • One place for "which answer wins." When sources disagree or overlap, ranking logic lives in one spot instead of five agents each deciding differently.
  • The only chokepoint for freshness and feedback. Tracking "is this stale" or "did an agent get corrected on this before" across every source only works if everything passes through one place.
Without it: you don't really have five sources — you have five × however many agents you deploy, each with its own copy of the integration and its own bugs.

What's actually in process & workflow context

This one is state, not knowledge — it changes by the hour. It's the only pillar that tells an agent where in the SDLC things currently stand, not just how the system is supposed to work.

What it tracks
tickets & issues PR & review status CI/CD run status release & deploy state feature flags
Typical MCP sources
GitHub MCP Jira / Linear MCP CI provider MCP release / deploy tooling
What it unlocks

agent asked to fix a bug → checks the ticket → checks if a PR already exists → checks if CI is currently red → decides: open a new PR, or pick up the existing one

Freshness is built in — it comes live from the MCP source itself, so there's nothing to re-index. The thing to get right here is write-scoping: an agent that can read ticket and PR state shouldn't automatically be able to close a ticket or merge a PR. That boundary belongs to trust & memory, not the source.

What's actually in runtime & operational context

This is the pillar most orgs don't already have an MCP server for — you're usually wrapping your own observability stack, which is why it's the real engineering effort in the rollout.

What it tracks
logs traces & spans metrics & SLOs active incidents prod config & flags
Where it usually lives
Datadog / Grafana / Splunk PagerDuty / Opsgenie feature-flag service postmortem archive
What it unlocks

"checkout failing for EU users" → agent pulls the failing trace → matches it to a recent deploy → matches a known error signature → opens a fix PR

The risk here isn't staleness, it's exposure. Raw logs and traces often carry PII or secrets, so this is the source that needs the trust & memory layer's redaction and scoping most, before any of it reaches an agent.

What's actually in the external knowledge graph

This is the source most people gesture at loosely. It's everything true about the world outside your repo and your platform: the libraries and APIs you depend on, what's wrong with them, and what the industry considers correct. The reason it's a graph and not just an indexed pile of docs is that the useful questions are relationship questions, not lookup questions.

What's in it — nodes
libraries & frameworks APIs & SDKs vendors & services security advisories (CVE / NVD) industry & compliance standards community knowledge
How they connect — edges
depends-on has-vulnerability deprecated-by compatible-with documented-by superseded-by
Why a graph beats a flat doc search

payments-sdk v2.1 → depends-on → auth-lib → has-vulnerability → CVE-2024-1234 → fixed-in → auth-lib v2.4

A doc search can tell you what a library does. Only a graph can answer "am I exposed" — by walking from what you use, to what it depends on, to what's wrong with that — three hops that never sit in the same document. That's the query an agent needs to run before it bumps a dependency, not after.

Kept fresh by: subscribing to package-registry advisories, the CVE/NVD feed, and vendor changelogs — not a one-time scrape. It's the fastest-changing source in the whole setup, which is exactly why it leans hardest on the trust & memory layer's freshness tagging.

What's actually in trust & memory

Not a source — a layer wrapped around all five of them. It's what keeps the whole setup honest past day one, instead of quietly going stale as your real system moves past its own documentation.

What it enforces
scoping & access control freshness / staleness flags provenance & trust score secrets & PII redaction
What it remembers
accept / reject signals review outcomes repeated corrections postmortem lessons
What it unlocks

agent proposes X → developer rejects it, ships Y instead → correction logged → next time the pattern shows up, the gateway ranks Y-style answers higher, for every agent

Why it's last, not optional: the other four primitives make the system accurate on day one. This is the only one that makes it get better over time instead of slowly drifting wrong.

03 — Impact

How each pillar accelerates the SDLC

The value isn't "more context" — it's that each stage of the SDLC draws on exactly the pillars it needs, automatically, instead of a developer manually assembling it.

04 — Rollout

Building it in order

Five sources and a trust layer is too much to build at once. Each step below has a plain test for "is this actually done" — build the next step only once you can pass the last one.

1

Make the static sources queryable

Wrap the repo, the platform catalog, and the external knowledge base so an agent can query each one directly.

Done when

An agent correctly answers "what does this service do" and "what's our convention for X."

2

Put a gateway in front

Give every agent one address to call instead of three-plus. The gateway decides where to look.

Done when

Swapping or adding a source doesn't require touching every agent's config, just the gateway.

3

Plug in process context

Point the gateway at the MCP servers you likely already have access to — GitHub, Jira or Linear, your CI provider. Mostly wiring, not building.

Done when

An agent can answer "is this PR blocked" or "did CI pass" with no custom connector written.

4

Build runtime context

Wrap your observability stack — logs, traces, metrics, incidents. This is the source that rarely ships an agent-ready MCP server, so it's the real engineering effort in the whole rollout.

Done when

An agent can tell the difference between "the docs say X" and "X is true in prod right now."

5

Turn on trust & memory

Scope what each agent can see, timestamp every answer, and log every accept/reject on agent output.

Done when

A mistake an agent got corrected on doesn't happen again from that same agent.

05 — Implementation

How you'd actually build each primitive

Every piece speaks the same protocol — MCP. Sources expose MCP tools, the gateway is MCP talking to MCP, and agents connect the same way no matter which source actually answered.

Sources

Build it as: each source gets its own small MCP server — a thin wrapper that turns "search the platform catalog" into a tool an agent can call.

Start with: local needs almost nothing — Claude Code already reads the repo. Platform is a wrapper over your service catalog's existing API. Process is mostly installing MCP servers that already exist (GitHub, Jira, CI). Runtime is a redacted, read-only wrapper over your observability API. External knowledge starts as a simple table — library, version, known issue, source — not a graph database on day one.

Gateway

Build it as: one more MCP server, whose tools call out to the source servers and merge the results. Agents only ever talk to this one.

Start with: simple rule-based routing — which tool name or keyword matches which source — is enough at first. You don't need a ranking model until sources actually disagree often enough to justify one.

Trust & memory

Build it as: two things bolted onto the gateway, not a separate system — a scoping check on every request, and a log of every response plus whatever accept/reject signal you can capture.

Start with: a table of {source, last-verified-at} for freshness, and a log of {query, response, accepted, correction} for memory. Enough to notice "this pattern got rejected three times" without a fancy re-ranker.

This follows the same order as the rollout above — most of it is wiring together MCP servers that already exist, not building new infrastructure. The part worth budgeting real engineering time for is runtime context and the feedback log; everything else is closer to configuration.

06 — Example

One bug fix, with and without context

Same ticket, same agent, same team — two different context setups. This is the actual difference the three primitives buy you.

The ticket

"Checkout total is wrong when a discount code is applied."

Without context
  1. Agent doesn't know the repo's test conventions — adds a new test file instead of extending the existing one. Style review sends it back.
  2. Agent doesn't know the discount logic actually lives in the shared pricing service — patches checkout locally, in the wrong place.
  3. Fix ships. It breaks another caller of that pricing function — caught by QA in staging, after merge.
  4. Ticket reopened. Fix redone against the real location.
With context
  1. LocalAgent follows repo conventions, extends the existing test file on the first try.
  2. PlatformAgent checks the capability catalog, finds the discount logic actually lives in the shared pricing service.
  3. PlatformAgent checks the dependency graph, finds the other caller, and adds a regression test for it before opening the PR.
  4. ProcessPR description is generated straight from the ticket's acceptance criteria. Reviewer approves on the first pass.
